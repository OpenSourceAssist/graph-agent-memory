= Connect Claude Desktop to Your Memory (TypeScript MCP Server)
:page-product: agent-memory
:page-pagination:
:toclevels: 3
:sectanchors:
:icons: font
:source-highlighter: highlight.js

A step-by-step tutorial to run a TypeScript MCP server that exposes the 12 standard memory tools to Claude Desktop, Cursor, or any MCP-aware client — backed by the hosted NAMS service.

[.lead]
In this tutorial we will stand up an MCP server in ~50 lines of TypeScript, register it with Claude Desktop, and watch Claude store entities, recall stored messages, and add reasoning traces during a normal chat — all backed by your NAMS account.

[TIP]
====
**Do you actually need to self-host?** Probably not. NAMS operates its own MCP server at `https://mcp.memory.neo4jlabs.com/mcp`, and it is a *larger* surface than the one you are about to build: scope-dependent tools spanning memory, entity review, ontology, workspace administration and Skills, with OAuth 2.0 so no long-lived key ends up in a config file. Adding it as a remote MCP server in your client is zero code — see xref:reference/nams-mcp.adoc[the hosted NAMS MCP server reference].

Self-hosting is the right choice when you want to **wrap, filter, or log tool calls** before they hit NAMS — to audit every call, expose a restricted subset to a particular client, add custom tools alongside the 12 memory ones, or proxy traffic from a network that can't reach `memory.neo4jlabs.com` directly. That's what this tutorial covers.
====

== What You'll Learn

* How to use `@neo4j-labs/agent-memory/mcp/register` to register the 12 standard memory tools on an MCP server in one call.
* How to wire that server to Claude Desktop via stdio.
* How to verify memory operations from a Claude chat.
* How to audit and restrict tool calls, and how to add a custom tool alongside the standard 12.

== Prerequisites

* Node.js 22 or later.
* An MCP client with local stdio-server support (the optional configuration example below uses Claude Desktop).
* `MEMORY_API_KEY` — get one at link:https://memory.neo4jlabs.com[memory.neo4jlabs.com].

== Time Required

About 15 minutes.

== Step 1: Project setup

[source,bash]
----
# From the repository root, build the current-source SDK first.
cd typescript
npm ci
npm run build
cd ..
mkdir my-memory-mcp
cd my-memory-mcp
npm init -y
npm install ../typescript @modelcontextprotocol/sdk@^1.30 zod@^4
npm install --save-dev typescript@^5.9 tsx@^4 @types/node@^22
mkdir src
----

This setup validates against the checkout; it does not assert which npm release
contains the shown APIs. Use the built package from this checkout for this lesson.

`zod` is what `McpServer` validates tool arguments with; it is an optional peer of the memory SDK and a direct dependency of the MCP SDK.

Add `"type": "module"`, an engine floor and the scripts to `package.json`:

[source,json]
----
{
  "type": "module",
  "engines": { "node": ">=22.0.0" },
  "scripts": {
    "start": "tsx --env-file-if-exists=.env src/server.ts",
    "build": "tsc -p tsconfig.json"
  }
}
----

Create `tsconfig.json` in `my-memory-mcp/`:

[source,json]
----
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "rootDir": "src",
    "outDir": "dist",
    "strict": true,
    "skipLibCheck": true
  },
  "include": ["src/**/*.ts"]
}
----

Merge the package fields above into the generated file; keep the dependency entries.
`--env-file-if-exists` is what loads `.env`; `tsx` does not read it on its own. Put your key there:

[source,bash]
----
echo 'MEMORY_API_KEY=nams_your_key_here' > .env
----

== Step 2: Write the MCP server

Create `src/server.ts`:

[source,typescript]
----
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { MemoryClient, VERSION } from "@neo4j-labs/agent-memory";
import { registerMemoryTools } from "@neo4j-labs/agent-memory/mcp/register";

async function main() {
  // Fail fast on stderr: thrown later, a missing key looks to the client like
  // a server that simply never answers.
  if (!process.env.MEMORY_API_KEY) {
    console.error("MEMORY_API_KEY is not set (see .env)");
    process.exit(1);
  }

  // Reads MEMORY_API_KEY from the environment Claude Desktop passes in.
  const memory = new MemoryClient();

  const server = new McpServer({ name: "my-memory-mcp", version: VERSION });

  // Registers all 12 memory tools: Zod-validated inputs, read/write
  // annotations, and dispatch to the matching MemoryClient method.
  const toolNames = registerMemoryTools(server, memory, {
    // One audit line per call — tool name and argument *keys*, never values.
    onCall: ({ tool, argKeys, durationMs, ok }) =>
      console.error(`[mcp] ${tool} keys=[${argKeys.join(",")}] ${durationMs}ms ok=${ok}`),
  });

  const transport = new StdioServerTransport();
  await server.connect(transport);
  console.error(`my-memory-mcp listening on stdio with ${toolNames.length} tools`);

  // Ctrl+C should close the MCP session and the memory client, not just die.
  for (const signal of ["SIGINT", "SIGTERM"] as const) {
    process.on(signal, () => {
      void (async () => {
        await server.close();
        await memory.close();
        process.exit(0);
      })();
    });
  }
}

main().catch((err) => {
  console.error(err);
  process.exit(1);
});
----

That's the whole server. `registerMemoryTools` covers this 12-tool SDK surface — definitions, schemas, annotations and dispatch — so the only code you own is policy: what to expose, what to log, and what to add.

Two things to note. Everything diagnostic goes to **stderr**: with the stdio transport, stdout is the protocol channel and a stray `console.log` corrupts it. And a dispatch failure comes back as a tool result with `isError: true` rather than a thrown protocol error, so Claude can read what went wrong and retry.

== Step 3: Test the server locally

[source,bash]
----
npm start
----

The process should print `my-memory-mcp listening on stdio with 12 tools` to stderr and then sit waiting for JSON-RPC over stdin/stdout. Press Ctrl+C to stop it.

If it exits 1 with `MEMORY_API_KEY is not set`, check that `.env` exists and that the `start` script carries `--env-file-if-exists=.env`.

== Step 4: Register the server with Claude Desktop

Client settings and UI labels change independently of this SDK. For a client
that uses `claude_desktop_config.json`, conventional locations include:

* **macOS**: `~/Library/Application Support/Claude/claude_desktop_config.json`
* **Windows**: `%APPDATA%\Claude\claude_desktop_config.json`

Add (or merge) the server config:

[source,json]
----
{
  "mcpServers": {
    "neo4j-memory": {
      "command": "node",
      "args": ["/absolute/path/to/my-memory-mcp/dist/server.js"],
      "env": {
        "MEMORY_API_KEY": "nams_..."
      }
    }
  }
}
----

Run `npm run build` first so `dist/server.js` exists. Pointing Desktop at compiled output keeps a TypeScript loader out of the launch path, which is the most common reason a server silently fails to start.

Use an absolute entry-point path and, if needed, an absolute Node executable
path. This server does not depend on a client-specific `cwd` setting.

`claude_desktop_config.json` is plaintext and this example passes the key through its `env` block, so use a workspace-scoped data-plane key rather than an admin key, and rotate it with `client.auth.rotateApiKey()` if the file leaks. If you would rather not keep a long-lived key on disk at all, use the hosted MCP server — it supports OAuth and this pattern cannot.

Restart Claude Desktop.

== Step 5: Verify the connection

Inspect the connected server's `tools/list` response in your MCP client. The
current SDK registers these 12 tools before any optional custom tool:

[listing]
----
memory_create_conversation
memory_add_messages
memory_get_context
memory_search_messages
memory_search_entities
memory_get_entity
memory_add_entity
memory_get_entity_history
memory_record_step
memory_record_tool_call
memory_get_trace
memory_explain_decision
----

If connection fails, inspect the client's MCP logs and the server's stderr.
The usual setup issues are:

* Wrong absolute path in `args`, or `dist/` not built yet.
* Missing or invalid `MEMORY_API_KEY` in `env` — the server exits 1 and says so in the log.
* Node not on the PATH that Claude Desktop sees — use the absolute path to the binary, e.g. `"command": "/usr/local/bin/node"`.

== Step 6: Store and read back a concrete memory

Ask the client to perform this sequence, retaining the actual returned ids:

[listing]
----
Create a memory conversation for tutorial-reader and show its returned id.
Add a user message to that conversation: "My fictional project is Lantern Orchard."
Get the context of that same conversation and show the stored message.
Add an organization entity named "Lantern Orchard tutorial" and show its id.
Get that entity by its returned id.
Record a step under the conversation describing these storage checks, then get its trace.
----

The deterministic checks are the returned message/entity data and recorded step.
The client's prose is illustrative; inspect successful tool results instead of
requiring a model to pick an exact sequence unaided. None of these 12 tools
creates a separate preference record.

== Step 7: Recall in a new client chat

Keep the NAMS conversation id from Step 6. In a new chat, supply that id:

[listing]
----
Use memory_get_context for NAMS conversation <the returned id>.
Search messages for "project" within that same conversation.
What project name was stored?
----

A new client chat does not automatically select the earlier NAMS conversation.
Message search requires its id. Entity search instead covers the authorized
workspace and need not be unique to this conversation. The SDK's offline MCP
registration/dispatch tests verify tool schemas and routing; a live client UI
and deployed extraction behavior require a separate manual check.

After the lesson, delete only the conversation and entity ids you created,
using the SDK or your workspace's resource controls. This 12-tool surface does
not include deletion tools. Avoid deleting a merged/shared entity merely
because its name matched the tutorial.

== Step 8: Add a custom tool

First add `import { z } from "zod";` beside the imports at the top of
`src/server.ts`. Then insert the following registration inside `main()`, after
`registerMemoryTools(...)` and before connecting the transport. It adds a read-only Cypher console — the single most useful thing a self-hosted server can expose, because it answers aggregate questions (`how many entities of each type?`) that no individual memory tool can:

[source,typescript]
----
// In src/server.ts, inside main(), after registerMemoryTools(...):
server.registerTool(
  "memory_cypher",
  {
    description:
      "Run a read-only Cypher query against the memory graph. Hosted NAMS only; " +
      "writes are rejected.",
    inputSchema: {
      cypher: z.string().describe("A read-only Cypher query."),
      params: z.record(z.string(), z.unknown()).optional(),
    },
    annotations: { readOnlyHint: true, idempotentHint: true, destructiveHint: false },
  },
  async ({ cypher, params }) => {
    try {
      const result = await memory.query.cypher({ cypher, params });
      return { content: [{ type: "text", text: JSON.stringify(result, null, 2) }] };
    } catch (err) {
      const message = err instanceof Error ? err.message : String(err);
      return { content: [{ type: "text", text: message }], isError: true };
    }
  },
);
----

`inputSchema` here is a Zod *raw shape* — a plain object of field schemas, not `z.object({...})`. `McpServer` turns it into the JSON Schema clients see and validates arguments against it before your callback runs, so `cypher` is already a `string` by the time you use it.

Treat this tool as privileged: anything the model writes runs against your graph. `client.query.cypher` rejects writes with HTTP 400, but you should still decide per client whether to register it at all.

Run `npm run build` again, then reconnect the client. The tool count should now be 13. Ask Claude:

[listing]
----
How many entities of each type do I have in memory?
----

Claude will call `memory_cypher` with something like `MATCH (e:Entity) RETURN e.type AS type, count(*) AS n ORDER BY n DESC` and read the rows back. You've just extended the MCP surface without touching the SDK.

== Step 9: Restrict what a client can reach

`registerMemoryTools` takes an allow-list. Anything not on it is neither advertised in `tools/list` nor callable:

[source,typescript]
----
const toolNames = registerMemoryTools(server, memory, {
  // e.g. MCP_TOOLS=memory_get_context,memory_search_entities
  only: process.env.MCP_TOOLS?.split(","),
  onCall: ({ tool, argKeys, durationMs, ok }) =>
    console.error(`[mcp] ${tool} keys=[${argKeys.join(",")}] ${durationMs}ms ok=${ok}`),
});
----

Replace the original registration block with this one; do not register the same
tools twice. The audit hook and allow-list apply to the registered memory tools.
Apply a separate policy to any custom Cypher tool you add.

== What You've Built

* An MCP server that exposes 12 (or 13) tools backed by NAMS memory, with validated arguments and read/write annotations.
* A wired-up Claude Desktop that reads and writes that memory automatically.
* An audit line per call and an allow-list — the two reasons to self-host rather than use the hosted server.
* A pattern for adding custom tools alongside the standard memory surface.

== Extending the Server

* **Filter what gets stored.** Wrap `registerMemoryTools` with your own `registerTool` for the writes you care about, and reject arguments that look like secrets or card numbers before dispatching.
* **Add per-tenant scoping.** Set `MEMORY_API_KEY` per Claude Desktop profile via different `mcpServers` entries — each profile reads and writes its own workspace.
* **Switch to Streamable HTTP.** Replace `StdioServerTransport` with `StreamableHTTPServerTransport` to run the server out-of-process (a sidecar, Cloud Run) and share it between clients:

[source,typescript]
----
import { StreamableHTTPServerTransport }
  from "@modelcontextprotocol/sdk/server/streamableHttp.js";

const transport = new StreamableHTTPServerTransport({
  sessionIdGenerator: () => crypto.randomUUID(),
});
await server.connect(transport);

// Then forward POST / GET / DELETE on your MCP route:
//   await transport.handleRequest(req, res, body);
----

The transport does not authenticate callers — put your own auth in front of the route. See xref:how-to/typescript/mcp.adoc[the MCP how-to] for the full listener, and the runnable example below for one you can copy.
