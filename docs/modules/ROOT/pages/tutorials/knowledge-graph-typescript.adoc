Store two synthetic documents as conversation messages, wait for a specific
extracted entity, and inspect the workspace graph returned by NAMS. Allow about
15 minutes. This lesson demonstrates ingestion and inspection. The service's
extraction pipeline decides which entities and relationships it produces; this
lesson does not promise a particular relationship or multi-hop traversal result.

== Step 1: Build the SDK and install the lesson project

This lesson uses the current source checkout. It does not establish which npm
release contains these APIs. Use Node.js 22 or later; the lesson project declares
AI SDK 7 and `@ai-sdk/openai` 4. You need a `MEMORY_API_KEY` for a test workspace
on link:https://memory.neo4jlabs.com/[NAMS]. NAMS performs extraction; this program does not need an OpenAI key.

From the repository root, run:

[source,bash]
----
cd typescript
npm ci
npm run build
cd examples/vercel-ai
npm ci
cp .env.example .env
----

Edit `.env` with your keys. Keep it out of version control. All remaining commands
run in `typescript/examples/vercel-ai/`. Its `package.json` sets ESM and its
`tsconfig.json` supplies the compiler settings; no global TypeScript install is needed.
Run `npm run lint` to verify the complete programs against your checkout.

== Step 2: Inspect the complete ingestion program

Open `src/tutorials/knowledge-graph.ts`. The program adds a conversation-specific
suffix to the fictional organization name to reduce confusion with an earlier
run. Entity search covers the workspace, so a count of unrelated results would
not establish readiness.

[source,typescript]
----
import { MemoryClient } from "@neo4j-labs/agent-memory";
import { pathToFileURL } from "node:url";

export async function inspectDocuments(client: MemoryClient, timeoutMs = 30_000) {
  const conversation = await client.shortTerm.createConversation({ userId: "tutorial-documents" });
  console.log(`CONVERSATION_ID=${conversation.id}`);
  const name = `Lantern Orchard ${conversation.id}`;
  await client.shortTerm.bulkAddMessages(conversation.id, [
    { role: "user", content: `${name} is a fictional organization that designs garden sensors.` },
    { role: "user", content: `Mira Vale is an engineer at ${name}. The team works in Willow Harbor.` },
  ]);
  const stored = await client.shortTerm.getConversation(conversation.id);
  console.log(`Stored documents: ${stored.messages.length}`);
  // Match this run's synthetic name; an arbitrary non-empty search is not readiness.
  const ready = await client.longTerm.waitForExtraction({
    query: name, expectedNames: [name], timeoutMs, intervalMs: 1_000,
  });
  if (!ready) {
    console.log("The expected entity was not found before the deadline. Messages remain stored.");
    return { conversationId: conversation.id, ready, entityIds: [] as string[] };
  }
  const entities = await client.longTerm.searchEntities(name, { limit: 10 });
  const matches = entities.filter((entity) => entity.name.toLowerCase() === name.toLowerCase());
  for (const entity of matches) console.log(`Entity: ${entity.id} ${entity.name} (${entity.type})`);
  const graph = await client.longTerm.getEntityGraph();
  console.log(`Workspace graph: ${graph.nodes.length} nodes, ${graph.edges.length} edges`);
  return { conversationId: conversation.id, ready, entityIds: matches.map((entity) => entity.id) };
}

if (process.argv[1] && import.meta.url === pathToFileURL(process.argv[1]).href) {
  const client = new MemoryClient({ endpoint: process.env.MEMORY_ENDPOINT });
  try {
    if (!process.env.MEMORY_API_KEY) throw new Error("Set MEMORY_API_KEY.");
    await inspectDocuments(client);
  } finally { await client.close(); }
}
----

`bulkAddMessages` accepts at most 100 messages per call. This lesson submits two.
`waitForExtraction` polls until a case-insensitive exact name match is present
or its deadline expires. A timeout returns `false`; authentication, network and
validation errors still propagate. The exact extracted name is not guaranteed,
so the timeout branch is an expected, useful result rather than proof of failed storage.

== Step 3: Run and distinguish storage from extraction

[source,bash]
----
npx tsx --env-file-if-exists=.env src/tutorials/knowledge-graph.ts
----

Expect `CONVERSATION_ID=<id>` and `Stored documents: 2` immediately after readback.
If the named entity becomes searchable, the program prints its actual id, name
and type, then workspace graph node/edge counts. Otherwise it prints the bounded
waiting message. Inspect stored documents even when extraction does not meet
the predicate; do not rerun ingestion merely to wait longer.

Graph output can include pre-existing workspace data. It is not a subgraph owned
by this conversation. Entity names, type assignments, edges and search order are
service outputs, and exact extraction/traversal behavior requires a separate live
sandbox check. These source-validated examples do not establish that live outcome.

== Clean up the conversation

Keep the printed conversation id. From the same lesson directory, delete that
specific conversation when you have finished inspecting it:

[source,bash]
----
CONVERSATION_ID='<the printed id>' npx tsx --env-file-if-exists=.env src/tutorials/conversation.ts cleanup
----

Closing the client only releases client resources. It does not delete stored
messages. Deleting a conversation does not promise removal of extracted,
workspace-wide entities; inspect those separately in a disposable test workspace.

Each run creates a new conversation and messages. Entity deduplication does not
make the whole script idempotent. Do not bulk-delete workspace entities to clean
up this lesson: they may be merged with data used by other conversations.
