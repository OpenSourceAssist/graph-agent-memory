:page-product: agent-memory

We will clone the healthcare template, activate a strict revision, inspect the active schema, and attempt a deliberately invalid entity write. Finally, we will restore the exact version that was active before the exercise and delete only the clone.

This lesson runs the maintained scripts from the current repository checkout in a POSIX shell. Offline checks verify the scripts and selected control flow; successful database, model, or hosted-service execution must still be observed in your environment. It does not claim that an unverified published SDK artifact exposes the same surface.

[[_before_you_begin]]
== Before you begin

* Python 3.10 or newer and Git.
* A dedicated NAMS test workspace and its *workspace key*, using `https://memory.neo4jlabs.com/v1`.
* Permission to create tutorial records in that workspace. Keep the same workspace key throughout the lesson.

See xref:reference/authentication.adoc[Authentication] for obtaining the key before beginning. This path uses a workspace key; admin keys and custom deployments belong in xref:how-to/use-nams.adoc[the NAMS guide].

Complete the xref:tutorials/nams-quickstart.adoc[NAMS lesson] first, retaining its checkout and virtual environment. This exercise also requires a `healthcare` template and an active ontology with a resolvable version ID. If either is absent, the program stops before changing the active schema. Do not run it concurrently with another ontology editor.

[[_step_5_clean_up]]
== 3. Run and check restoration

[source,bash]
----
python docs/modules/ROOT/examples/ontology_quickstart.py
----

Expected milestones:

. `Previous active version:` and `Exercise clone:` show the captured version and the new ontology ID.
. `Strict schema entity labels:` displays the active template's actual labels.
. `Verified: strict validation rejected the unknown type` confirms the observed rejection. If the service accepts the write, the program fails and prints its entity ID for inspection.
. `Restored active version:` matches the first version ID.
. `Deleted exercise clone:` matches the clone ID, after restoration was verified.

Restoration also runs if the exercise fails after cloning. If restoring or verifying the prior version fails, the clone is retained and the error propagates; use the printed IDs to inspect the workspace. Removing the clone alone would not restore the prior active version.

[[_what_you_learned]]
== What we learned

A schema version and its active binding are separate resources. Strict validation is a service behavior that must be observed, and schema cleanup is a state-restoration operation. The fixture does not delete unrelated entities or reset the workspace.
