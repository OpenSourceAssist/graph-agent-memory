= Expose memory as tools
:source-highlighter: rouge

The `@neo4j-labs/nams-ai-provider` package talks only to the hosted Neo4j
Agent Memory Service (NAMS) at https://memory.neo4jlabs.com — it has no Bolt
equivalent for a self-managed Neo4j database.

Tools mode gives the model two explicit AI SDK tools, `query_memory` and
`store_memory`, instead of injecting memory into the prompt automatically.
The model decides when to call them, and every call is visible in your UI —
useful when you want memory activity on screen for debugging, or when you
want the model to search and write memory deliberately rather than on every
turn. This page walks through a complete, runnable program that teaches the
agent a preference in one turn and recalls it with a fresh tool set in the
next.

A runnable copy of this program, alongside the other three modes, lives at
link:https://github.com/neo4j-labs/agent-memory/tree/main/typescript/examples/nams-ai-provider[`typescript/examples/nams-ai-provider`].

Prerequisites:

* Node.js 22 or newer (the package's declared floor).
* A `MEMORY_API_KEY` from https://memory.neo4jlabs.com[memory.neo4jlabs.com].
* The packages installed:
+
[source,bash]
----
npm install @neo4j-labs/nams-ai-provider@0.3.0 @neo4j-labs/agent-memory@0.5.0 ai@^7 @ai-sdk/openai@^4 zod@^4
----

== The program

.Save as `tools-mode.ts`
[source,typescript]
----
/**
 * Tools mode: the model decides when to read and write memory, and each
 * memory call shows up as a visible tool call. `enforceQueryMemory()` makes
 * sure `query_memory` runs before the model can give a final answer.
 * `ensureMemoryStored()` persists the turn if the model never called
 * `store_memory` itself. Turn 1 teaches a preference; turn 2 uses a fresh
 * tool set for the same user, so the only way to answer is `query_memory`.
 *
 * Run with:
 *
 *   MEMORY_API_KEY=nams_... OPENAI_API_KEY=sk-... npx tsx src/tools-mode.ts
 *
 * Expected output (arguments and wording vary):
 *
 *   --- Turn 1 -- teach it something
 *   step 0 [enforced: some tool required]
 *     tool call: query_memory({"query":"user editor preferences","limit":5})
 *   step 1 [unconstrained]
 *     tool call: store_memory({"content":"User prefers very short answers", ...
 *   ensureMemoryStored: already-stored
 *   assistant: Got it -- short answers, and I'll remember you use Neovim.
 *
 *   --- Turn 2 -- fresh tool set, same user
 *   step 0 [enforced: some tool required]
 *     tool call: query_memory({"query":"editor preferences","limit":5})
 *   assistant: You use Neovim, and you like short answers.
 */

import { createNams, enforceQueryMemory, ensureMemoryStored } from '@neo4j-labs/nams-ai-provider';
import { openai } from '@ai-sdk/openai';
import { ToolLoopAgent, stepCountIs, type LanguageModel } from 'ai';

const userId = process.env.NAMS_DEMO_USER ?? 'demo-user-tools-mode';
const modelId = process.env.NAMS_DEMO_MODEL ?? 'gpt-5.4-mini';

/**
 * Run the teach-then-recall demo. `buildModel` defaults to OpenAI; tests pass
 * a mock model factory here so the demo can run without a real API call.
 */
export async function toolsModeDemo(
  buildModel: (id: string) => LanguageModel = openai,
): Promise<{ taught: string; recalled: string }> {
  const apiKey = process.env.MEMORY_API_KEY;
  if (!apiKey) {
    throw new Error(
      'Set MEMORY_API_KEY before running this example. Get a free key at https://memory.neo4jlabs.com',
    );
  }

  const nams = createNams({
    apiKey,
    endpoint: process.env.MEMORY_ENDPOINT,
    workspaceId: process.env.MEMORY_WORKSPACE_ID,
  });

  async function turn(label: string, prompt: string, instructions: string): Promise<string> {
    // A new tool set each turn -- store_memory/query_memory read and write
    // the same NAMS-side conversation for this user, found by userId.
    const tools = nams.tools({ userId });

    const agent = new ToolLoopAgent({
      model: buildModel(modelId),
      instructions,
      tools,
      prepareStep: enforceQueryMemory(), // holds the model at query_memory until it has queried
      onFinish: async event => {
        // Falls back to persisting the answer if store_memory was never called.
        const outcome = await ensureMemoryStored(tools)(event);
        console.log(`ensureMemoryStored: ${outcome.stored ? 'persisted the turn' : outcome.reason}`);
      },
      stopWhen: stepCountIs(6),
    });

    const result = await agent.generate({ prompt });

    console.log(`\n--- ${label}`);
    let queried = false;
    result.steps.forEach((step, i) => {
      console.log(`step ${i} [${queried ? 'unconstrained' : 'enforced: some tool required'}]`);
      for (const call of step.toolCalls) {
        queried ||= call.toolName === 'query_memory';
        console.log(`  tool call: ${call.toolName}(${JSON.stringify(call.input).slice(0, 120)})`);
      }
    });
    console.log(`assistant: ${result.text}`);
    return result.text;
  }

  const taught = await turn(
    'Turn 1 -- teach it something',
    'I prefer very short answers, and I use Neovim. Got any editor tips for me?',
    'Consult memory with query_memory before answering. When the conversation ' +
      'contains facts or preferences worth remembering, call store_memory before ' +
      'giving your final answer.',
  );

  const recalled = await turn(
    'Turn 2 -- fresh tool set, same user',
    'What editor do I use, and how do I like my answers?',
    'Consult memory with query_memory before answering.',
  );

  return { taught, recalled };
}

if (import.meta.url === `file://${process.argv[1]}`) {
  toolsModeDemo().catch(err => {
    console.error(err);
    process.exit(1);
  });
}
----

== Procedure

. Read the demo `userId` and model id from the environment, falling back to
  `demo-user-tools-mode` and `gpt-5.4-mini`.
. Require `MEMORY_API_KEY`. `toolsModeDemo` throws immediately with a link to
  get a key if it's unset.
. `createNams({ apiKey, endpoint, workspaceId })` builds one memory client
  for the whole demo. `endpoint` and `workspaceId` come from optional
  environment variables.
. Define a `turn(label, prompt, instructions)` helper that builds a **fresh
  tool set each turn** — `store_memory`/`query_memory` read and write the
  same NAMS-side conversation for this user, found by `userId` — and runs an
  agent loop:
+
--
* `nams.tools({ userId })` returns `{ query_memory, store_memory }`.
* `new ToolLoopAgent({ model, instructions, tools, prepareStep:
  enforceQueryMemory(), onFinish, stopWhen: stepCountIs(6) })`.
  `enforceQueryMemory()` is passed with no options, so it uses its default
  `graceSteps: 3`: it holds the model at `toolChoice: 'required'` until
  `query_memory` has run, then forces `query_memory` directly if it still
  hasn't run by step 3.
* `onFinish` calls `ensureMemoryStored(tools)(event)` and logs whether it
  persisted the turn or found nothing to do — the fallback for when the
  model answered without ever calling `store_memory`.
* `agent.generate({ prompt })` runs the loop. The program then logs each
  step's tool calls, prefixed with whether `query_memory` had already run by
  that step (`enforced: some tool required` before it has, `unconstrained`
  after), and finally the assistant's text.
--
. Call `turn()` twice with different instructions:
+
--
* Turn 1 ("teach it something") tells the model to consult memory before
  answering and to call `store_memory` when the conversation contains facts
  or preferences worth remembering, then states an editor preference.
* Turn 2 ("fresh tool set, same user") only instructs the model to consult
  memory before answering — a fresh `nams.tools({ userId })` call, but the
  same NAMS-side data — and asks a question whose answer only exists in what
  turn 1 stored.
--
. Return `{ taught, recalled }` so a caller (here, the offline test suite) can
  assert on both answers.

== Run and verify

From `typescript/examples/nams-ai-provider/`, after the workspace build and
`.env` setup described in the example's README:

[source,bash]
----
npx tsx --env-file-if-exists=.env src/tools-mode.ts
----

Expected output (arguments and wording vary with the model):

[source,text]
----
--- Turn 1 -- teach it something
step 0 [enforced: some tool required]
  tool call: query_memory({"query":"user editor preferences","limit":5})
step 1 [unconstrained]
  tool call: store_memory({"content":"User prefers very short answers", ...
ensureMemoryStored: already-stored
assistant: Got it -- short answers, and I'll remember you use Neovim.

--- Turn 2 -- fresh tool set, same user
step 0 [enforced: some tool required]
  tool call: query_memory({"query":"editor preferences","limit":5})
assistant: You use Neovim, and you like short answers.
----

Turn 2's answer is the actual check: no local state carries the preference
from turn 1 to turn 2, so the model can only answer by calling
`query_memory` and reading back what turn 1's `store_memory` call wrote.

== Tools mode specifics

`createNams(config).tools(scope)` (synchronous, no MCP) returns a plain AI
SDK `ToolSet`, `{ query_memory, store_memory }`.

`query_memory`:: Input `{ query: string, limit: number (1–20, default 5) }`.
Searches the same five memory sources as the other modes and returns each
match as a `MemoryHit`, so a result with `source: "graph"` is a stored
relationship, written `(subject)-[RELATIONSHIP]->(object)`.
`store_memory`:: Input `{ content: string (≤2000 chars), type:
"fact"|"interaction"|"pattern"|"user_preference", confidence: number (0–1,
default 0.7), tags: string[] (≤10, ≤40 chars each) }`. `type: "interaction"`
is saved as a plain conversation message; every other type creates (or
reuses) a flat `Entity` — unless `extractionModel` is set, see below.

`enforceQueryMemory({ graceSteps = 3 })` is a `prepareStep` hook that makes
retrieval mechanical instead of advisory. Until a step's tool calls have
included `query_memory`, it sets `toolChoice: 'required'` — the model can
still call other tools in any order, but cannot finish with a text-only
answer before querying memory. Once `stepNumber` reaches `graceSteps`
without a query having run, that step's `toolChoice` becomes `{ type:
'tool', toolName: 'query_memory' }` — with the default `3`, steps 0 to 2 get
`'required'` and step 3 itself is forced — so the loop can
never exhaust its step budget without the query having run. Keep
`graceSteps` at least two below your `stopWhen` budget so the forced query
and the final answer both still fit; `{ graceSteps: 0 }` forces the query as
the literal first step.

`ensureMemoryStored(tools, { fallback? })` is an `onFinish` hook that closes
the write-side gap `prepareStep` can't: the loop ends the moment the model
emits final text, so there's no later step left to force `store_memory`
into. It **must** receive the exact `tools` object returned by `.tools()`
(or `.toolsWithMcp()` / `createNamsMemoryTools()`) — spreading it into a copy
(`{ ...tools }`) loses the binding to the memory client and the call throws
immediately. If `store_memory` already ran this turn it does nothing
(`{ stored: false, reason: 'already-stored' }`); otherwise it calls
`fallback({ text, toolNames })` (default: the final assistant text saved as
an `interaction`, or nothing if `text` is empty) and persists the result,
returning `{ stored: true, input }`, `{ stored: false, reason:
'nothing-to-store' }`, or `{ stored: false, reason: 'failed' }` on a caught
write error.

=== MCP tool merging

Still tools mode, not a fifth mode: `nams.toolsWithMcp(scope, { url,
headers?, toolPrefix?, optional? })` connects to an MCP server and merges its
tools with `query_memory`/`store_memory` into one `ToolSet`. It lazily
imports the optional peer `@ai-sdk/mcp` — only when an MCP config is passed —
so it adds no dependency weight for callers who never use it. `toolPrefix`
namespaces the MCP tool names to avoid clashing with the NAMS tools; without
a prefix, a name collision is logged as a warning and the MCP tool wins.
With `optional: true`, a connection failure degrades to memory-only tools
instead of throwing: `close()` becomes a no-op and the result's `mcp.error`
carries a `NamsMcpConnectionError` whose message names the required auth
scheme when the server answered with a 401. No runnable example in this
repository exercises `toolsWithMcp` yet, so treat the snippet below as a
partial illustration, not a complete program:

[source,typescript]
----
const { tools, close } = await nams.toolsWithMcp(
  { userId },
  {
    url: 'https://mcp.example.com/mcp',
    headers: { Authorization: `Bearer ${token}` },
    toolPrefix: 'mcp_',
    optional: true,
  },
);
// tools: query_memory, store_memory, mcp_* -- or memory-only if the
// connection failed and optional: true degraded it.
----

=== Graph extraction (`extractionModel`)

Tools mode is the only mode that accepts `extractionModel` /
`extractionOptions` (on `createNams({ extractionModel, extractionOptions })`
or directly on `createNamsMemoryTools`). When set, a `store_memory` call of
type `fact`, `user_preference`, or `pattern` runs through
`createGraphExtractor(extractionModel, extractionOptions)` — one extra model
call per memory that pulls out named entities and the relationships between
them and writes them as graph nodes and edges, instead of one flat
sentence-shaped `Entity`. The extractor skips self-referential entities (an
agent's summary of what it remembers about "remembering" itself) by default;
`extractionOptions.skipEntity` overrides that filter. `createNamsProvider`
and `createNamsMemory` do not accept `extractionModel` or `extractionOptions`
(removed in 0.3.0); setting them on `createNams()` and then calling `.wrap()`
or `.hooks()` is a no-op that logs one warning — those modes persist turns as
short-term messages, which NAMS already extracts server-side, so extracting
again client-side would just duplicate that work.
