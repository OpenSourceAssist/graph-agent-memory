# Documentation review: unified feedback and action plan

**Date:** 2026-09-17
**Branch:** `docs-review`
**Commit:** `bf14d3d`
**PR:** #257 — "docs: align guides and examples with current SDK behavior"

**Method:** 12 page groups (entry, tutorials Python/Aura, tutorials hosted+TypeScript, how-to core, how-to ops, how-to providers/hosted, how-to integrations, how-to TypeScript, reference core, reference hosted, reference API, explanation) reviewed by three personas each — a Diataxis editor, an accuracy verifier who read the corresponding source in `src/neo4j_agent_memory/` and `typescript/src/`, and a target reader. Seven further personas swept the corpus: backend scope, versioning, Neo4j code style, Labs brand, diagrams, information architecture/navigation, and build. Every finding was then independently re-verified by a separate pass that re-opened the cited file and the cited source symbol; 173 candidate findings survived to a verdict; after the orchestrator's post-synthesis spot-check of every blocker, 152 are confirmed and 21 refuted. Models: Claude Sonnet 5 for review and verification, Claude Opus 5 for this synthesis, Claude Fable 5.1 orchestrating and spot-checking the blockers.

**Scope.** Everything under `docs/modules/ROOT/` (112 pages, partials, `examples/`, `images/`, `nav.adoc`), plus `docs/MAINTAINING.md`, `docs/diagrams/manifest.json`, `nav.adoc`, the four repository skills, and the SDK sources the docs make claims about.

**Not checked.** No live services: nothing was run against Aura, NAMS, or any paid model API, so no tutorial was executed end to end. The published site at neo4j.com/labs/agent-memory was not fetched; only the in-repo Antora sources. The TypeScript test suite (`cd typescript && npm test`) was never run, so PR #257's "512 TypeScript tests pass" is neither confirmed nor refuted. External link targets (GraphAcademy, Wikipedia, vendor docs) were checked for presence in prose, not resolved over the network. Deliberate exceptions recorded in `docs/MAINTAINING.md` (fonts, casing of real property names, Aura instead of Docker) were treated as policy, not defects.

## 1. Executive summary

- **The corpus is in good shape and the PR is close, but it is not mergeable as it stands.** Eight blockers remain across seven Phase 0 tasks: four code samples that raise on the first line a reader copies, two entry pages with no Labs disclaimer, an install line that pulls a package version the guide's own code cannot use, and a set of pages that contradict each other about the pinned 0.6.0 release.
- **PR #257's "no warnings or broken links" claim survived; its test count did not.** The reviewers first flagged nine `include::example$` targets as missing, but all nine resolve through `docs/extensions/example-files.json` to files under `examples/`, exactly as `docs/MAINTAINING.md` describes, and the fresh Antora build emits no warning; those three findings are refuted in Appendix B [howto-ops-accuracy-2, howto-ops-accuracy-3, howto-providers-hosted-accuracy-2]. The "605 documentation tests pass" figure is still not reproducible from the commands `docs/MAINTAINING.md` documents; those produce 281 passed / 144 skipped [build-1].
- **Theme 1 — the docs were verified against the wrong tree.** Pages pin `==0.6.0`, but this branch is eight commits behind `main` and its `src/` is still 0.5.0, so the corpus contradicts itself about one method: `how-to/entities.adoc:30` correctly states 0.6.0 returns the persisted entity ID, while `reference/api/long-term.adoc:36` still prescribes a Cypher readback workaround for the bug 0.6.0 fixed and `how-to/deduplication.adoc:64` describes pre-0.6.0 merge coverage [ref-api-accuracy-1, ref-api-accuracy-2, howto-core-accuracy-1, howto-core-accuracy-2, ref-api-reader-3].
- **Theme 2 — a small number of copy-paste code samples are simply wrong.** `client.short_term.get_messages()` does not exist on the NAMS client [howto-providers-hosted-accuracy-1]; `GLiNEREntityExtractor.for_schema("ecommerce")` raises `ValueError` [howto-ops-reader-1]; `MemoryDependency(memory_client=...)` is not a field of that dataclass [howto-integrations-accuracy-1]; `message.created_at` is not a stored graph property [neo4j-style-1]. Each is a one-line fix, and each is the *first* code a reader on that page runs.
- **Theme 3 — structure drifts out of quadrant in predictable places.** Three Python NAMS tutorials each carry the same ~90 lines of reference-shaped recovery boilerplate and a five-branch decision table [tut-nams-ts-diataxis-1, -2]; `how-to/integrations/index.adoc` reproduces ten integrations' install commands and code instead of linking [howto-integrations-diataxis-3]; `how-to/typescript/integrations-overview.adoc` is a five-language reference catalogue filed as a TypeScript how-to [howto-typescript-diataxis-3].
- **Two Labs policy gaps sit on entry points.** `sdks/python.adoc` carries no Labs disclaimer at all while its sibling `sdks/typescript.adoc` carries the full block, and `getting-started.adoc` has neither disclaimer nor support link — against `docs/MAINTAINING.md:95` [entry-diataxis-1, labs-brand-1, labs-brand-2].
- **Strengths worth protecting:** `reference/backend-capabilities.adoc` as a genuinely careful capability matrix; the `// contract: <file>:<Class>.<method>` traceability comments on every API reference entry; the "Prepare → Apply → Run and verify" how-to template with exact expected output; ~960 internal xrefs with zero dead targets; and the corpus's habit of documenting its own bugs (the unapplied `session_id` filter) rather than hiding them.

## 3. What is working

- **`reference/backend-capabilities.adoc` is the load-bearing page of this PR and it earns it.** It splits Python/Bolt, Python/NAMS and TypeScript/NAMS per operation, names which kwargs the NAMS wrapper silently drops, and states real sharp edges rather than parity. Nearly every other reference page links to it.
- **Source traceability in the API reference is exemplary.** Every entry under `reference/api/` carries a `// contract: <file>:<Class>.<method>` comment. Verifiers used those comments to check roughly fifteen methods per page against `src/` and found the signatures, keyword-only markers and defaults exact.
- **The how-to template is real and testable.** The five core recipe pages (`messages`, `entities`, `preferences`, `deduplication`, `reasoning-traces`) all run Prepare the client → Apply the task function → Run and verify, ending with an exact expected string rather than "you should see...".
- **Negative documentation heads off the most common wrong guesses.** `how-to/entities.adoc` states outright that there are no Python `update_entity`, `delete_entity`, `merge_entities` or `get_entity` wrappers; `entity-extraction-schemas.adoc` names the eight registered GLiNER schemas and explicitly denies `financial`/`ecommerce`.
- **Navigation integrity is genuinely good.** 111 of 112 pages are reachable from `nav.adoc` (the exception, `configuration.adoc`, is a deliberate legacy-redirect stub), every nav xref resolves, each quadrant index enumerates its whole directory, and ~960 internal cross-references produced no dead target.
- **The corpus documents its own bugs instead of hiding them.** The unapplied `session_id` filter in Bolt semantic message search, `add_relationship` dropping `attributes`, `geocode_locations` ignoring `skip_existing=False`, and `VertexAIEmbeddingProvider` not forwarding `dimensions` are all disclosed, and all four were verified true in source.
- **Anchor preservation actually works.** Restructured pages carry `anchor:` shims — `configuration.adoc` alone holds 66 compatibility targets — so old deep links keep resolving. This is the PR claim that holds up best.
- **The TypeScript how-to group is the strongest reader experience in the corpus** (`reader:howto-typescript` mean 4.83). Every page ends with a named offline verification command, and pages lead with what is *not* supported (`mastra.adoc`'s "not a Mastra storage adapter" box) rather than glossing.
- **Diagram tooling, where it is used, has real provenance.** `docs/diagrams/manifest.json` and `scripts/manage_diagrams.py` record source and output SHA-256, exporter version and review date, and validate dangling bindings. The core memory/POLE+O/buffered-write diagrams follow the documented semantic palette, and alt text describes content rather than naming a file.
- **Explanation pages stay in register.** Thirteen pages of rationale and tradeoffs with no numbered procedures, each opening with a Bolt-vs-NAMS NOTE and closing with cross-quadrant links. `extraction-pipeline.adoc:50` even records a prior documentation error rather than silently correcting it.

## 4. Key themes

### 4.1 The docs were verified against a stale tree

`docs-review` is eight commits behind `origin/main`, and `main` changed `memory/long_term.py` and `graph/query_builder.py` in the commits that became 0.6.0. Pages verified against local `src/` therefore describe 0.5.0 while pinning `==0.6.0`, and pages verified against the release describe 0.6.0 — so the corpus now contradicts itself about `add_entity`'s return ID and about what `merge_duplicate_entities` transfers. **Fix pattern:** rebase onto `origin/main`, then re-verify every claim tagged to a version against the released tree, never against the working branch; add that rule to `docs/MAINTAINING.md` next to the existing HEAD-vs-published note. [ref-api-accuracy-1, ref-api-accuracy-2, ref-api-reader-3, howto-core-accuracy-1, howto-core-accuracy-2, tut-python-aura-accuracy-1, tut-python-aura-accuracy-2]

### 4.2 Maintained-example includes resolve through a manifest the page does not mention (refuted blocker)

Three accuracy reviewers, the verification pass and the synthesis pass all concluded that nine `include::example$` targets across `running-without-an-llm.adoc`, `evaluation.adoc` and `team-memory-in-your-editor.adoc` pointed at missing files. They do not: `docs/extensions/example-files.js` registers those nine resource names from `docs/extensions/example-files.json`, which maps each to an existing file under `examples/`, and `make docs-lint` fails on a genuinely unresolved include. The three findings are refuted [howto-ops-accuracy-2, howto-ops-accuracy-3, howto-providers-hosted-accuracy-2] and tasks P0-1 and P1-1 are withdrawn. What survives is a discoverability observation, not a defect: nothing near the include tells a maintainer that `example$no_llm/main.py` is a virtual resource, and `docs/MAINTAINING.md` is the only place that says so. **Fix pattern (optional, minor):** a one-line AsciiDoc comment above each manifest-mapped include naming the repository path it resolves to.

### 4.3 First code block failures

Five separate pages open with a snippet that cannot run: a nonexistent NAMS method, an unregistered GLiNER schema name, a wrong dataclass keyword, a nonexistent node property, and an npm install of a package version that lacks the middleware the page then uses. Accuracy verification was deep on *signatures inside reference pages* and thin on *the first snippet of a how-to*. **Fix pattern:** fix the five, then bias the next review pass toward the opening code block of every task page — that is where a reader's trust is won or lost. [howto-providers-hosted-accuracy-1, howto-ops-reader-1, howto-integrations-accuracy-1, neo4j-style-1, versioning-1]

### 4.4 Quadrant bleed at index and tutorial boundaries

The same content appears in three shapes: tutorials carrying reference decision tables, index pages carrying full recipes, how-to pages carrying rationale. The three Python NAMS tutorials duplicate ~90 lines of recovery guidance verbatim while their TypeScript twins already solve exactly this with `include::partial$typescript-tutorial-lifecycle.adoc[]`. **Fix pattern:** the TypeScript route already shows the answer — extract shared lifecycle/recovery prose into partials, move decision tables to how-to or reference, and reduce index pages to a scannable list plus xrefs. [tut-nams-ts-diataxis-1, tut-nams-ts-diataxis-2, tut-nams-ts-diataxis-3, tut-nams-ts-reader-1, tut-nams-ts-reader-2, howto-integrations-diataxis-3, howto-integrations-diataxis-5, howto-typescript-diataxis-3, howto-typescript-diataxis-4, howto-ops-diataxis-1, howto-providers-hosted-diataxis-1, howto-core-diataxis-6, tut-python-aura-diataxis-1, tut-python-aura-diataxis-2]

### 4.5 One page, three names

At least nine pages are labelled differently in `nav.adoc`, in their quadrant index, and in their own H1 — `multi-tenancy.adoc` is "Multi-Tenant Memory" in nav and "Associate memory with users and select scoped reads" in its title and index. Two unrelated pages share the nav label "MCP Tools". A reader building a mental model of the sidebar cannot match it to the page they land on. **Fix pattern:** one sweep over `nav.adoc` and the four index pages making label = H1 (sentence case), with a `tests/docs/` assertion that nav label, index link text and page title agree. [howto-ops-diataxis-3, ia-nav-4, howto-core-diataxis-4, howto-providers-hosted-diataxis-2, howto-providers-hosted-diataxis-4, ref-api-diataxis-1, ref-hosted-diataxis-2, ref-core-reader-6, tut-python-aura-diataxis-5, howto-integrations-diataxis-7, labs-brand-3]

### 4.6 The diagram estate is untended

Fifty-five files in `images/diagrams/` against 27 manifest entries, one PNG embedded twice on the same page under different alt text, a `.png.bak`, a `poleo-model2.png`, an unwired `multi-tenant-scoping.png` that a page needs, and no diagram at all on the two most structural topics (Bolt vs NAMS, and every TypeScript page). **Fix pattern:** triage the 28 untracked files (wire or delete), then extend `check_manifest()` to flag files that appear in neither the manifest nor any page reference — turning orphan accumulation into a build warning. [explanation-diataxis-2, diagrams-1, diagrams-2, diagrams-3, diagrams-4, diagrams-5, diagrams-6, diagrams-7, explanation-reader-3]

### 4.7 Hedging has crowded out the value proposition

Caveats are individually true and often verified — but on entry pages nearly every sentence has a "X does not imply Y" clause, `index.adoc` and `getting-started.adoc` show zero code while `sdks/typescript.adoc` shows a full Quick Start, and `reader:entry` scored 3.14 against a 4.58 accuracy mean. The docs are accurate and unpersuasive at the same time. **Fix pattern:** keep the caveats but relocate them — one summary sentence plus an xref to `backend-capabilities.adoc` on entry pages, the full hedge on the reference page that owns it — and put a five-line Python snippet on the landing page. [entry-reader-2, entry-reader-3, entry-reader-5, howto-providers-hosted-reader-3, ref-core-reader-3, ref-core-reader-5, howto-core-reader-7, tut-python-aura-diataxis-3]

### 4.8 Labs policy is applied unevenly across entry points

`docs/MAINTAINING.md:95` requires the full Labs disclaimer on site entry points. `index.adoc` and all three READMEs comply; `sdks/python.adoc` has no "Labs", "SLA" or "community" string anywhere, and `getting-started.adoc` has neither disclaimer nor support link — while the sibling `sdks/typescript.adoc` carries the full `[IMPORTANT]` block. `typescript/README.md:4` additionally says Beta where the rest of the project says Experimental. **Fix pattern:** make the disclaimer a partial, include it from every page `nav.adoc` lists at top level, and pick one lifecycle badge across all READMEs. [entry-diataxis-1, labs-brand-1, labs-brand-2, labs-brand-5, labs-brand-4, labs-brand-7]

### 4.9 Missing explanation pages push rationale into how-to

There is no explanation-quadrant page for the v0.2 operational primitives (buffered writes, consolidation, evaluation) or for the TypeScript "three-tier context" model that every TS how-to page assumes, so tradeoff prose leaks into task pages and the "reflections"/"observations" tiers used on ten pages appear in no glossary entry. **Fix pattern:** two new explanation pages plus three glossary rows, then delete the leaked paragraphs and xref instead. [howto-ops-diataxis-6, howto-typescript-diataxis-7, ia-nav-5, howto-typescript-diataxis-8, explanation-diataxis-4]
